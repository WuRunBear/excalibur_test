# 方案 C：前端完全服务端权威渲染重构目标

## 1. 背景

当前 `excalibur_test` 已经具备联机基础能力，但游戏层仍保留较多“本地单机逻辑”：

- `src/game/actors/player.ts` 仍会直接读取键盘并修改本地坐标。
- `src/game/scenes/main.ts` 会创建本地玩家 Actor，并通过快照回调把本地位置同步给 UI。
- `src/game/index.ts` 负责输入上行，但 UI 中的玩家位置仍主要来自本地玩家快照，而不是服务端 `RoomState`。
- `src/game/world/entityStore.ts`、`src/game/world/actorManager.ts`、`src/game/world/mapTileMap.ts` 已经具备“服务端状态驱动渲染”的基础能力，但尚未成为主链路。

这导致前端存在两套并行思路：

- 一套是“本地玩家渲染 + 本地位置驱动 UI”。
- 一套是“服务端状态下行 + 插值渲染实体”。

后续若继续做碰撞、战斗、技能、同步动画与调试视图，这种“双轨结构”会持续增加维护成本。因此需要在后续迭代中执行一次方案 C 重构，把前端正式收敛为“完全服务端权威、前端仅负责输入与表现”的结构。

## 2. 重构目标

方案 C 的目标不是简单把渲染接到后端，而是把前端游戏层整体调整为“网络状态驱动型”架构。

完成后应满足以下结果：

- 前端不再存在本地权威玩家位置。
- 所有实体位置、血量、存在性都以服务端 `RoomState` 为唯一事实来源。
- 本地输入只负责表达意图，并通过网络发送到服务端，不直接修改场景对象。
- 主场景只承载显示层，不再承担本地玩家模拟职责。
- 地图、实体、碰撞调试体、UI 状态都围绕服务端下行状态组织。
- 保留客户端插值，但不做客户端预测、回滚或本地碰撞修正。

## 3. 非目标

本方案不包含以下内容：

- 不实现客户端预测与服务端校正。
- 不实现回滚同步。
- 不在前端做权威碰撞。
- 不重做现有 Vue UI 架构。
- 不要求一次性补齐战斗、动画、技能等全部联机表现层。

## 4. 目标架构

重构后的前端游戏层建议拆分为四类职责明确的模块。

### 4.1 网络会话层

建议新增独立的网络会话模块，例如 `src/game/net/session.ts`，负责：

- 建立和断开 Colyseus 连接。
- 管理房间引用。
- 订阅 `RoomState` 变化。
- 维护“本地玩家对应的服务端实体 id”。
- 拉取地图运行时数据与碰撞调试快照。

该层只关心“网络数据从哪里来、如何订阅、如何发送输入”，不直接操作 Excalibur 场景。

### 4.2 渲染世界层

建议新增独立的渲染世界模块，例如 `src/game/world/renderWorld.ts`，负责：

- 创建和维护地图可视层。
- 持有 `ActorManager`。
- 持有调试碰撞体管理器。
- 每帧接收实体快照并落地到 Excalibur `Scene`。
- 在断线、切场景或销毁时清理全部 Actor 与调试对象。

该层只关心“如何把已经准备好的快照渲染出来”，不承担输入与网络职责。

### 4.3 输入控制层

建议把键盘输入采集独立为输入控制模块，例如 `src/game/input/inputController.ts`，负责：

- 读取键盘状态。
- 把按键映射为 `InputPayload`。
- 处理发送节流。
- 维护朝向推导等纯输入语义。

该层不直接修改场景，不依赖玩家 Actor，不持有服务端状态。

### 4.4 UI 状态映射层

建议新增 UI 状态适配层，例如 `src/game/ui/uiStateAdapter.ts`，负责：

- 把服务端实体快照映射为 `GameUIState`。
- 根据本地玩家实体 id 选取当前玩家的坐标、血量等字段。
- 维护 FPS、连接状态、提示消息等客户端附加状态。

这样 `MyGame` 将不再直接同时处理“引擎、网络、UI、输入”的所有细节，而是只做总装配。

## 5. 文件级改动目标

### 5.1 `src/game/index.ts`

目标：

- 从“单体引擎控制器”调整为“装配层”。
- 负责创建网络会话、输入控制器、渲染世界、UI 状态适配器。
- 保留 `initGame()` 和 `destroyGame()` 这类对外稳定入口。

重构后它应只协调模块之间的调用顺序，而不是承载所有业务逻辑。

### 5.2 `src/game/scenes/main.ts`

目标：

- 删除本地玩家创建逻辑。
- 不再依赖 `PlayerSnapshot`。
- 保持为一个薄场景，仅负责每帧把 Excalibur 生命周期委托给外部控制器。

### 5.3 `src/game/actors/player.ts`

目标：

- 从当前项目主链路中退场。
- 若仍保留，应仅作为历史兼容文件，不能继续承担本地权威玩家职责。
- 更理想的状态是删除该文件，并统一使用 `EntityActor` 表示玩家和 NPC。

### 5.4 `src/game/world/entityStore.ts`

目标：

- 保持“轻量插值缓存”职责。
- 继续作为服务端快照的唯一渲染输入缓存。
- 必要时可补充重置接口，用于断线与重新连接后的清空。

### 5.5 `src/game/world/actorManager.ts`

目标：

- 继续承担“快照表 -> Actor 增删改”的职责。
- 支持本地玩家高亮。
- 后续可扩展颜色、渲染层级、动画状态等表现字段。

### 5.6 `src/game/world/mapTileMap.ts`

目标：

- 作为服务端地图运行时的可视化层。
- 负责把阻挡格渲染到场景。
- 可进一步容纳“碰撞调试体 Actor”的生成或交由独立调试管理器处理。

### 5.7 `src/game/net/types.ts`

目标：

- 与服务端协议保持同步。
- 当前应补上 `CollisionDebugSnapshot.pairs` 字段，确保调试数据结构一致。

## 6. 核心数据流

重构后的主数据流应固定为：

1. 用户按键。
2. 输入控制层采集按键，生成 `InputPayload`。
3. 网络会话层把输入发送给服务端。
4. 服务端推进 ECS，并把权威状态写回 `RoomState`。
5. 客户端收到 `RoomState` 增量更新。
6. `EntityStore` 写入最新快照并维护插值缓存。
7. 渲染世界层在每帧从 `EntityStore.sample()` 读取插值结果。
8. `ActorManager` 把采样结果落地为场景中的实体 Actor。
9. UI 状态映射层根据本地玩家实体 id，从服务端快照生成 `GameUIState`。

必须禁止出现以下反向链路：

- 本地 Actor 改位置后再回写 UI。
- 本地玩家位置覆盖服务端实体位置。
- UI 直接读取 Excalibur Actor 作为权威状态来源。

## 7. 场景与表现约束

方案 C 下，场景层必须遵守以下约束：

- 场景中不存在“专属本地玩家逻辑”。
- 场景中的所有可见角色统一视为服务端实体表现层。
- 本地玩家与远端玩家的差异只体现在高亮、镜头跟随或 UI 聚焦，不体现在权威位置来源。
- 若需要镜头跟随，应以“本地玩家对应的服务端实体 Actor”为跟随目标。

## 8. UI 状态来源约束

`GameUIState` 中的玩家状态应按以下原则生成：

- `player.x/y`：来自服务端实体快照。
- `player.facing`：短期内可继续由本地输入推导；中长期更适合由服务端同步明确朝向字段。
- `stats.hp`：来自服务端实体状态。
- `fps`：继续由客户端本地计算。
- 连接状态与提示消息：来自客户端连接事件。

换句话说，UI 中只有“纯本地展示状态”可以由客户端维护，游戏世界状态必须来自服务端。

## 9. 调试能力目标

方案 C 应把调试视图也纳入正式结构，而不是零散挂在网络请求旁边。

建议后续补齐：

- 调试碰撞体管理器，负责把 `/debug/colliders` 数据落地为调试 Actor。
- 调试开关状态，允许 UI 控制是否显示地图碰撞体、实体碰撞体、碰撞对。
- 调试数据刷新节流，避免每帧拉取调试接口。

## 10. 迁移策略

建议按以下顺序重构，而不是一次性全部替换：

### 阶段一：切断本地权威

- 主场景停止创建本地 `Player`。
- `MyGame` 的 UI 坐标来源切到服务端快照。
- `ActorManager` 正式成为主渲染链。

### 阶段二：抽离模块

- 抽出网络会话层。
- 抽出输入控制层。
- 抽出 UI 状态映射层。
- `MyGame` 退化为装配器。

### 阶段三：补齐调试与表现

- 接入碰撞调试渲染。
- 增强实体表现字段。
- 视需要补镜头跟随、朝向同步、动画状态同步。

## 11. 验收标准

当方案 C 完成时，应满足以下验收条件：

- 前端不再创建本地权威玩家 Actor。
- 拔掉服务端下行状态后，前端无法继续驱动玩家移动。
- 玩家与 NPC 都通过统一的服务端实体快照渲染。
- UI 中的坐标与血量来自服务端实体状态。
- 断线、重连、切场景时，场景内实体与地图对象可正确清理和重建。
- 碰撞调试数据结构与服务端保持一致。

## 12. 风险与注意事项

- 若在未完成服务端权威链切换前删除本地 `Player`，会短暂失去玩家显示，需要先确保 `ActorManager` 已接上 `RoomState`。
- 若 UI 仍保留对本地玩家快照的隐式依赖，会出现“画面以后端为准，但 UI 位置仍是旧本地值”的双源问题。
- 若不补重置逻辑，断线重连后 `EntityStore` 和 `ActorManager` 可能残留旧实体。
- 若后续要把朝向也完全交给服务端，需要同步扩展服务端协议。

## 13. 结论

方案 C 的本质不是“把前端渲染接一下后端”，而是把 `excalibur_test` 从“本地玩家为核心的演示结构”升级为“网络状态驱动的正式联机前端结构”。

下次启动该重构时，应以本文件为目标说明，优先按“先切断本地权威，再抽离模块，最后补齐调试表现”的顺序推进，避免一次性大改导致验证困难。
